# 한 달치 가상 투표·주간 리포트 검증

이 검증은 [이슈 #207](https://github.com/sugkamoney/geupjido-backend/issues/207)의 백엔드 리포트 시뮬레이션이다. 로컬 PostgreSQL·PostGIS의 `geupjido` DB를 전용 `geupjido_weekly_report_month_smoke` DB로 복제하고, **복제본에서만** 기존 투표·리포트 데이터를 비운다. 개발 RDS와 서비스 투표 데이터는 사용하지 않는다. 원본 DB의 투표·리포트 행 수를 실행 전후 비교하고 검증 DB를 삭제한다.

## 실행

저장소 루트에서 다음을 실행한다.

```bash
docker compose up -d postgres
python3 -B scripts/test/weekly-report-month-smoke.py
```

스크립트는 검증 DB가 이미 있으면 중단한다. 실패하더라도 검증 DB 정리를 시도한다. 테스트는 DB 이름을 다시 확인한 다음 데이터를 변경한다. 상위 셸의 DB 접속 변수는 실행 환경으로 넘기지 않으며, `Clock`을 주입해 시간을 이동시키므로 컴퓨터의 시계는 바꾸지 않는다. 예약 작업은 끈 상태로 발행 서비스를 직접 실행하고, 목록·상세 HTTP 응답은 `MockMvc`로 확인한다.

## 시나리오

- 2026년 11월 8일·15일·22일·29일, 네 번의 일요일 **18시 마감 → 21시 공개**를 순서대로 재현한다.
- 두 구의 권역 4곳에 단지 2곳씩 배치한다. 매주 서로 다른 가상 방문자 10명이 서로 다른 단지 대진 10판씩 선택한다. 권역마다 주당 권역 간 표 50표와 방문자 10명을 얻어, 실제 전환 기준 **유효표 50표·방문자 10명·권역 간 표 20표**를 충족한다.
- 다섯 번째 권역은 매주 1표만 받아 `INITIAL`/수집 중으로 남긴다. 첫 주에는 같은 방문자의 같은 날 동일 대진 1표를 추가로 저장해 유효표 제외를 확인한다. 첫 마감 정각에 기록한 1표는 첫 주에서 빠지고 둘째 주에 포함된다.
- 첫 주와 다음 주들에서 초안 비공개, 21시 공개, 중복 발행 방지, 주간 참여자·유효표, 급지 구간 변경, 상승·하락, 급지 경계, 수집 중, 구별 변화, 이전·다음 탐색을 검증한다. 과거 발행본의 내용은 다음 주에도 유지되며 탐색용 `nextReportId`만 새 발행본에 맞게 갱신된다.

이 시나리오는 저장된 가상 게임·선택을 **실제 집계·발행 서비스**에 넣는다. 쿠키와 투표 저장 HTTP 경로 자체는 기존 [가상 방문자 HTTP 검증](worldcup-virtual-voters-smoke.md)의 범위다.

## 2026-11-20 검증 결과

| 마감일(KST) | 해당 주 유효 방문자 | 해당 주 유효표 | 급지 구간 변경 | 많이 오른 권역 | 많이 내린 권역 | 구별 변화 |
|---|---:|---:|---:|---|---|---:|
| 11월 8일 | 11명 | 101표 | 비교 불가 | 없음 | 없음 | 없음 |
| 11월 15일 | 12명 | 102표 | 2곳 | sim-a, sim-c | sim-d, sim-b | 2개 구 |
| 11월 22일 | 11명 | 101표 | 3곳 | sim-d, sim-b | sim-c, sim-a | 2개 구 |
| 11월 29일 | 11명 | 101표 | 0곳 | sim-b | sim-c, sim-d | 2개 구 |

`worldcup_vote`에는 406표가 저장됐지만, 같은 날 동일 대진 1표를 제외한 유효표는 405표였다. 첫 주 18시 정각의 표는 둘째 주 102표에 포함됐다. 모든 주에서 수집 중 권역과 급지 경계 목록이 반환됐다. 검증 DB는 종료 후 삭제됐고 원본 DB의 `worldcup_vote`·`weekly_report`·`weekly_report_zone_snapshot` 행 수는 `4|0|0`으로 유지됐다. 이 수치는 가상 시나리오의 기대값이며 실제 서비스 사용자 통계가 아니다.

넷째 주에는 소수 첫째 자리 급지가 움직인 권역이 있어 상승·하락 목록은 채워졌지만, **1~5급지 구간 자체는 바뀌지 않아** `changedGradeZoneCount`가 0이었다. 두 값의 기준이 다르다는 점도 함께 검증했다. 요약 문장은 네 주 모두 각 주의 집계로 생성됐고, 첫 리포트에는 전주 비교 표현이 없었다.

전체 테스트와 빌드는 저장소 규칙에 따라 별도로 `./gradlew clean build`로 확인한다. 실제 일요일 예약 실행의 장시간 가동·동시 사용자 요청·개발 서버 데이터량은 이 빠른 시간 이동 테스트의 검증 범위에 포함되지 않는다.
