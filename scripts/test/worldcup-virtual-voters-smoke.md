# 가상 방문자 HTTP 투표·예약 집계 검증

관련 이슈: [#175](https://github.com/sugkamoney/geupjido-backend/issues/175)

## 목적과 실행

월드컵 선택이 실제 HTTP·쿠키 요청으로 저장되고 예약 집계 뒤 지도 상태와 권역·단지 순위에 반영되는지 확인한다. 로컬 Docker의 `geupjido-postgres`, Java와 Python 3이 필요하다. 저장소 루트에서 다음 명령 하나로 실행한다.

```bash
python3 -B scripts/test/worldcup-virtual-voters-smoke.py
```

스크립트는 JAR를 빌드하고 로컬 `geupjido` DB를 별도 `geupjido_worldcup_virtual_voters` DB로 복제한다. 복제본의 기존 월드컵 게임·선택·건너뛰기와 발행 표 수만 지운다. 원본 로컬 DB와 공유 개발 RDS의 선택 기록은 변경하지 않는다. 기존 브라우저 검증 DB(`geupjido_worldcup_browser_smoke`)도 사용하거나 삭제하지 않는다. 전용 DB가 이미 있거나 로컬 18080번 포트를 다른 프로세스가 쓰면 중단한다.

앱은 이 복제 DB를 바라보는 `dev` 프로필로 `127.0.0.1:18080`에서만 실행한다. 상위 셸의 다른 Spring DB 설정은 앱 프로세스에 전달하지 않는다. **이 프로세스에서만** 예약 Cron을 15초 간격, HTTP 쿠키의 `Secure`를 꺼서 테스트한다. 저장소의 프로필 기본값과 실제 개발 서버의 한국 시간 3시간 예약은 바꾸지 않는다.

## 검증 흐름

1. 시작 가능한 권역 중 아직 `INITIAL`인 권역을 고른다.
2. 서로 다른 쿠키 저장소를 가진 가상 방문자 10명이 각각 게임 1개를 시작하고 9판씩 선택한다. 각 방문자의 저장된 진행 상태를 같은 쿠키로 다시 조회한다.
3. 총 선택 90표와 권역 간 선택 20표 이상을 확인한다. 실제 쿠키 식별자와 개인 정보는 출력하지 않는다.
4. 마지막 선택 뒤 예약 발행이 실행될 때까지 기다린다. 지도 상태의 발행 유효표 **90표**, 참여자 **10명**, 선택한 권역의 유효표 **90표**를 확인한다.
5. 선택한 권역이 `VOTE`로 전환됐고 투표 급지와 적어도 한 단지의 점수·권역 내 순위가 있는지 확인한다.
6. 앱을 종료하고 전용 검증 DB를 삭제한다. DB 생성에 성공한 뒤 검증이 실패해도 앱 종료와 DB 삭제를 시도하며 앱 로그 끝부분을 출력한다.

이는 Python HTTP 클라이언트의 쿠키 저장소로 브라우저의 요청 흐름을 재현하는 테스트다. 실제 브라우저의 `HttpOnly` 접근 제한과 CORS는 [별도 브라우저 검증](worldcup-browser-smoke.md)에서 확인한다. 로컬에서 15초로 단축한 예약 실행을 검증하며 실제 개발 서버의 3시간 주기나 장시간 가동을 대신 검증하지는 않는다.

## 실행 결과

2026-11-14 로컬 PostGIS에서 통과했다. 가상 방문자 10명이 HTTP로 90표를 저장했고, 그중 권역 간 선택은 55표였다. 예약 발행 후 지도 상태는 유효표 90표·참여자 10명, 검증 권역은 유효표 90표와 `VOTE` 급지를 반환했다. 점수·순위가 있는 단지 13곳도 확인했다. 검증 전용 DB는 실행 뒤 삭제됐다. 선택할 권역과 대진은 데이터와 무작위 생성에 따라 달라질 수 있으므로, 55표와 단지 13곳은 고정된 합격 기준이 아니다.
