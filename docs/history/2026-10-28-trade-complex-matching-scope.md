## 확인한 데이터

2026-10-28 로컬 PostgreSQL·PostGIS의 `apartment_trade`에는 2026년 9월 용산구(`11170`) 거래 34행이 있다. `complex_id`와 `zone_id`가 채워진 행은 없다. 표본은 한 시군구·한 달에 한정되므로 전체 수집 결과의 매칭률로 일반화하지 않는다.

아래 조사는 [`location-mapping.json`](../../data/location/mapping/location-mapping.json)의 용산구 권역 여섯 개를 기준으로 했다. 이촌·한남·서빙고·한강로·원효·후암 권역의 법정동만 포함한 로컬 표본 분류다. 실거래가 API는 시군구 단위로 조회하므로 이 범위 밖 법정동의 원본 거래도 함께 저장될 수 있다.

| 분류 | 거래 행 | 원본 단지·주소 조합 | 확인된 내용 |
| --- | ---: | ---: | --- |
| 서비스 대상, 같은 지번 후보 1개 | 18 | 14 | 후보 18건의 거래 건축연도와 단지 사용승인연도는 같았다. 정규화한 이름까지 같은 거래는 6건이다. |

여기서 지번 후보는 `complex.legal_dong_code` 앞 5자리와 거래 시군구 코드를 비교하고, `complex.address_jibun`에 `법정동명 + 지번` 문자열이 있는지 찾은 **탐색 결과**다. 이후 후보 주소에서 추출한 지번을 거래 지번과 다시 비교해 18건 모두 문자열상 정확히 일치함을 확인했다. 필지나 건물 동일성 검증은 아직 하지 않았다. 18건을 즉시 연결 가능한 건수로 해석하면 안 된다.

## 매칭 전 확인할 차이

- 실거래가 원본은 5자리 시군구 코드와 법정동 **이름**을 주고, 단지 마스터와 권역 매핑은 10자리 법정동 **코드**를 쓴다. 전체 지역에서 재사용할 이름↔코드 대응 방법이 필요하다.
- 이름이 다른 12건은 같은 지번·연도 후보가 있더라도 단지명 변형 또는 단지 구분을 확인해야 한다.
- 대상 5건의 거래 지번과 마스터 지번은 일치하지 않는다. 특히 거래 `센트럴파크`의 한강로3가 98에는 [서울시 건축물대장](https://openab.seoul.go.kr/build/detail.do?mgmBldrgstPk=10041100226360)이 `센트럴파크` 공동주택을 표시한다. 로컬 마스터의 `용산센트럴파크`는 한강로3가 63-70이므로 이름만 보고 같은 단지로 묶지 않는다.
- 서비스 대상 밖 11건은 원본 거래를 보존하되, 존재하지 않는 권역을 만들거나 인근 단지에 연결해서는 안 된다. 이후 대표 시세 집계도 서비스 대상 연결 거래만 사용해야 한다.

## 서비스 대상 밖 거래 처리 결정

2026-10-28 사용자 결정: 현재 권역 정의를 유지한다. 그 기준에서 대상 밖으로 분류된 법정동 거래 11건은 수집 원본을 `apartment_trade`에 보관하되 `complex_id`와 `zone_id`를 채우지 않는다. 대상 밖이라는 이유만으로 원본을 삭제하거나 인근 단지에 연결하지 않는다.

이 결정은 현재 로컬 표본의 분류에 적용했다. 다른 시군구에서도 동일하게 판단하려면 법정동 이름을 10자리 코드로 확인하고, 그 코드가 서비스 권역에 있는지 검사하는 방식이 필요하다. 동일 이름의 법정동이 여러 지역에 있을 수 있으므로 이름만으로 범위를 판단하지 않는다.

## 법정동 코드 참조 자료 준비

로컬에서 사용하던 행정안전부 법정동 코드 원본 `legal-dong-codes-20260917.txt`는 Git 제외 파일이다. [행정표준코드관리시스템](https://www.code.go.kr/stdcode/regCodeL.do?menuNo=101010100010)의 법정동 코드 전체자료를 내려받은 2026-09-17 스냅샷이다. 공공데이터포털의 [행정안전부 법정동 코드 안내](https://www.data.go.kr/data/15077871/openapi.do)는 제공기관과 이용허락범위를 확인하는 근거다.

`scripts/location/build_legal_dong_reference.py`가 원본에서 현재 존재하는 서울·인천·경기 읍면동 1,370개를 추려 `data/location/reference/legal-dongs-20260917.tsv`를 생성한다. 이 참조 파일은 Git에 포함해 새 환경에서도 같은 코드 기준을 사용한다. 생성 과정에서 현재 권역 매핑의 법정동 코드 255개가 모두 포함되는지 검사한다. 원본 추출 파일과 대조한 차이는 `경기도 여주시 대신면` 뒤의 공백 하나를 정리한 것이다.

`LegalDongCodeReferenceReader`는 참조 파일을 읽어 `시군구 코드 + 법정동 이름`으로 10자리 법정동 코드를 찾는다. 중복된 코드 또는 같은 시군구 안의 중복 이름은 실패한다. 조회 실패를 서비스 범위 밖으로 취급하지 않는다.

`ApartmentTradeScopeClassifier`는 조회된 법정동 코드가 권역 매핑에 있으면 `IN_SCOPE`와 권역 ID를, 코드가 확인되지만 권역 매핑에 없으면 `OUT_OF_SCOPE`를 반환한다. 참조 자료에서 코드를 찾지 못하면 `UNKNOWN_LEGAL_DONG`으로 남긴다. 권역 매핑에 참조 자료가 모르는 코드가 있으면 생성 시 실패한다. 이 판별은 단지 매칭 또는 DB 갱신을 수행하지 않는다.

`ComplexRepository.findByLegalDongCode`와 `ApartmentTradeCandidateFinder`는 대상 거래와 같은 10자리 법정동 코드의 단지만 조회하고, 주소의 `법정동명 + 지번`을 독립된 토큰으로 비교한다. 예를 들어 거래 지번 `417`은 단지 주소 `417-1`에 걸리지 않는다. 이 단계는 후보 목록만 반환하며 이름·건축연도·동일 건물 여부를 최종 판정하거나 DB를 갱신하지 않는다. 관련 단위 테스트와 `./gradlew clean build`가 통과했다.

`ApartmentTradeCandidateAssessmentService`는 후보 수를 먼저 확인하고, 단일 후보가 있으면 거래 건축연도와 단지 사용승인연도를 비교한다. 연도가 같을 때 이름의 **공백만 제거**해 `NAME_EXACT` 또는 `NAME_REVIEW`로 구분한다. `NAME_EXACT`도 자동 연결 결정이 아니다. 후보 없음·복수 후보·연도 누락·연도 불일치도 별도 상태로 반환한다. 이 단계에서는 거래의 외래 키를 수정하지 않는다.

로컬 DB에서 `district_code`, `legal_dong_name`별 거래 수를 읽기 전용으로 집계하고 같은 참조 파일·권역 매핑에 대조했다. 34건 중 `IN_SCOPE` 23건, `OUT_OF_SCOPE` 11건, `UNKNOWN_LEGAL_DONG` 0건이다. 이 수치는 현재 로컬 2026년 9월 용산구 표본에 대한 검증이며, 다른 월·지역의 결과를 보장하지 않는다.

## 대상 거래 23건의 단지 후보 조사

로컬 거래의 법정동 이름·지번을 단지 마스터의 지번주소와 대조했다. 아래 표는 같은 지번의 **후보**가 하나씩 나온 14개 원본 단지·주소 조합이며, 거래 행으로는 18건이다. 모두 거래 지번과 후보 주소에서 추출한 지번이 일치한다. 후보의 10자리 법정동 코드는 참조 자료의 거래 법정동 코드와 같고, 거래 건축연도와 후보 사용승인연도가 같으며, 후보 단지에 권역 ID가 있다. 이 검사는 **현재 로컬 DB에 있는 후보**만 대상으로 했고, 다른 주택의 동일 지번 사용이나 건물 동일성까지 증명하지 않는다. 이름이 다른 조합도 있으므로 아직 연결을 확정하지 않았다.

후보 탐색기와 같은 법정동 코드·지번 경계 조건을 로컬 PostgreSQL에 읽기 전용으로 적용하면 대상 23건 중 후보 1개가 18건, 후보 없음이 5건, 복수 후보는 0건이다. 이는 탐색 조건을 SQL로 재현한 결과이며 애플리케이션의 DB 갱신 실행 결과는 아니다.

같은 SQL 조회에 현재 판정 서비스의 연도·공백 제거 이름 규칙을 적용하면 `NAME_EXACT` 4건, `NAME_REVIEW` 14건, `NO_CANDIDATE` 5건이다. 연도 미확인·불일치와 복수 후보는 0건이다. 앞서 조사한 이름 일치 6건은 **공백과 기호를 함께 제거한 탐색 기준**이므로 현재의 보수적인 `NAME_EXACT` 4건과 정의가 다르다.

따라서 현재 확인된 것은 **대상 23건의 분류와 후보 현황**이다. 실제 거래의 `complex_id`·`zone_id`는 아직 비어 있다. 같은 지번 후보 18건은 이름 차이와 단지 동일성을 더 확인해야 한다. 후보 없는 5건은 **현재 로컬 단지 마스터의 해당 지번에 없는 거래**다. K-apt 원천 자체에 없는지, 주소가 변경됐는지, 다른 공식 단지 ID가 있는지는 확인되지 않았다. 이름이 비슷한 다른 지번 단지에 연결하지 않는다.

## 이번 이슈의 처리 순서

1. 34건 모두 서비스 범위를 판별한다. 대상 23건과 대상 밖 11건을 구분한다.
2. 대상 23건을 고유 원본 단지·주소 단위로 대조한다. 동일 지번 후보 14조합의 이름 차이와 지번 후보 없는 4조합을 각각 검증한다.
3. 확인된 단지만 `complex_id`와 그 단지의 `zone_id`를 함께 채운다. 근거 없는 연결을 만들지 않는다.
4. 전체 지역에 적용할 법정동 이름↔코드 대응과 재처리 정책을 정한 뒤 구현한다.

진행 이슈는 [#96](https://github.com/sugkamoney/geupjido-backend/issues/96)이다. 이 점검 단계에서 로컬 DB의 거래·단지 값은 변경하지 않았다.

## 연결 제안과 수동 적용 구현

같은 지번 후보가 한 개인 14개 원본 조합을
[`yongsan-202609-proposals.tsv`](../../data/trade/matching/yongsan-202609-proposals.tsv)에
기록했다. 최초 작성 시 **14개 모두 `PENDING`**이었다. 그중 공백만 제거한 이름이 같은
조합은 3개, 이름 검토가 필요한 조합은 11개다. 제안 파일은 현재 후보를 사람이
확인하기 위한 목록이며, 승인 결과가 아니다.

[K-apt 공식 서울 목록](https://www.k-apt.go.kr/cmmn/introMmentPop.do?bjdCode=11&searchOccuDate=202609&upYn=Y)에서
14개 후보의 지번주소와 사용승인연도를 다시 확인했다. 조합별 대조와 이름 차이는
[`yongsan-202609-review.md`](../../data/trade/matching/yongsan-202609-review.md)에
기록했다. 단일 지번 후보와 이름 차이를 대조한 결과 12조합은 승인 권장,
`리첸시아용산A`와 `한성1` 2조합은 동·동차 표기의 범위를 추가 확인할
대상으로 분리했다. 공식 K-apt 목록은 실거래 원본의 별칭까지 증명하지
않는다. 이후 사용자는 12조합을 승인했고 두 조합은 보류했다.

`ApartmentTradeLinkService`는 `APPROVED` 행에 한해 현재 단지 ID·이름·법정동
코드·사용승인연도·권역을 다시 확인한다. 원본 거래의 서비스 범위, 단일 후보,
이름 판정도 다시 검사한 뒤 `complex_id`와 해당 단지의 `zone_id`를 함께 채운다.
같은 연결을 재실행하면 건너뛰며, 기존의 다른 연결이나 변경된 후보가 있으면
트랜잭션 전체가 실패한다. `PENDING`과 `REJECTED`는 건드리지 않는다. 수동
Runner는 설정이 명시적으로 켜진 경우에만 동작한다. 실행 방식과 파일 열 설명은
[`data/trade/matching/README.md`](../../data/trade/matching/README.md)에 있다.

최초 구현은 승인된 원본 조합과 일치하는 기존 모든 월의 거래를 찾았다.
사용자가 2026년 9월 표본만 승인한 뒤, 검토 파일 각 행에 계약월을 추가했다.
현재 승인된 행은 2026년 9월 계약 거래만 연결하며 다른 월은 건드리지 않는다.
같은 원본 조합이라도 다른 계약월은 별도의 행으로 검토·승인해야 한다.
한 검토 파일에 여러 월·시군구의 승인 행을 담을 수 있다.
앞으로 수집할 새 거래에 자동으로 연결하는 흐름과 대표 시세 집계는 이
표본 적용에 포함하지 않았다.

같은 지번 후보가 없는 5건은 현재 단지 마스터와 연결할 ID가 없다. 공식 자료로
주소나 건물의 존재가 일부 확인되더라도, 이를 다른 지번 단지의 ID로 대체할 수
없다. 해당 지번의 실제 단지 ID 또는 원천 수집 누락 여부를 확인한 뒤 별도 제안을
만들어야 한다. 서비스 범위 밖 11건은 기존 결정대로 원본만 보관한다.

## 로컬 적용 결과와 전체 서비스 범위

2026-10-28에 승인된 12조합을 로컬 DB의 **2026년 9월 용산구** 거래에 수동
적용했다. `apartment_trade` 34건 중 `complex_id`와 `zone_id`가 모두 채워진
거래는 16건이다. 연결된 거래의 `zone_id`와 해당 `complex.zone_id`가 다른
건은 0건이다. 나머지 18건은 보류 2건, 같은 지번의 단지 후보가 없는 5건,
현재 서비스 권역 밖 11건이다. 앞부분의 연결 전 수치는 조사 시점의 기록이다.

이 계약월과 시군구는 첫 검증 표본이다. 서비스의 목표 범위는 현재 권역 매핑에
포함된 **모든 지역의 거래**이며, 새로운 계약월에도 같은 분류·확인·연결
흐름을 적용해야 한다. 특정 아파트에 거래가 없으면 연결할 실거래가도 없다.
원본 API에 단지 고유 ID가 없으므로, 서비스 대상 거래라도 동일 단지라는 근거가
부족하면 연결을 보류한다. 용산구 승인 파일을 다른 월·지역에 자동 재사용하지
않는다.

현재 수집 Runner는 시군구 한 곳과 계약월 하나를 수동으로 입력받는다. 연결
Runner는 계약월이 각 행에 적힌 승인 파일을 수동으로 적용한다. 별도 수동
점검 Runner는 저장된 모든 거래를 페이지 단위로 읽어 대상 여부, 후보 판정,
기존 연결 상태를 `build/reports/apartment-trade-match-audit.tsv`에 기록한다.
점검 결과는 로컬 34건 전부, 대상 23건, 대상 밖 11건, 법정동 미확인 0건,
연결 16건, 연결 불일치 0건이다. 미연결 대상 7건은 이름 검토 2건과 후보
없음 5건이다. 이 점검은 DB를 변경하지 않는다.

서비스 대상 전 지역의 월별 반복 수집·연결과 예약 실행은 아직 구현되지
않았다. 예약 수집은 #96 이슈의 제외 범위에 따라 후속 작업으로 진행한다.

계약월을 승인 행의 키로 둔 뒤, 같은 원본 조합의 10월 거래를 임시로 넣는
PostgreSQL 통합 테스트에서 9월 승인만으로는 10월 거래가 연결되지 않고,
10월 승인 행을 추가하면 그 거래만 새로 연결되는 것을 확인했다. 이미 연결된
9월 거래 16건은 재실행 시 모두 `이미 연결`로 집계됐다. 로컬 실제 수동
Runner 재실행도 신규 0건·이미 연결 16건으로 끝났다. 전수 점검 보고서는
헤더를 포함해 35행이며 DB 거래 34건이 한 번씩 기록됐다.
`RUN_POSTGIS_IT=true` 통합 테스트와 `./gradlew clean build`가 성공했다.
GitHub Actions CI는 브랜치를 푸시한 뒤 확인해야 한다.

새 월 수집은 기존처럼 **원본 저장이 먼저**다. 이번 구현은 저장 경로에서 후보를
자동 승인하지 않는다. 이후 같은 원본 조합의 거래가 생기면 검토 파일의 대응이
여전히 맞는지 확인하고 수동 연결을 다시 실행한다. 연결 실패는 수집 결과를
변형하거나 다른 단지로 대체하는 대신 오류를 보고하고 연결 트랜잭션을
롤백한다. 재수집에서 기존 거래를 찾으면 현재 저장 로직은 정상 거래를 건너뛰고
정상→해제만 갱신하므로 연결된 단지·권역은 유지된다. 해제→정상 또는 해제일
불일치는 기존 정책대로 오류가 난다. 연결된 해제 거래도 연결 값은 보존하되,
후속 대표 시세 집계에서는 제외해야 한다.
