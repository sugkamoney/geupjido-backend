# 전체 주간 실거래가 갱신 검증

관련 이슈: [#212](https://github.com/sugkamoney/geupjido-backend/issues/212).

## 대상과 격리

2026-11-21의 권역 매핑에는 시군구 62곳이 있다. 주간 갱신 기본 범위인
2026년 9~11월은 총 186개 시군구·계약월 조합이다. 전체 실행은 로컬
`geupjido` DB의 복제본에서 수행했다. 실행기는 접속 DB를 전용 복제본으로
고정하고 원본의 거래·연결·충돌·대표 가격 집계를 실행 전후 비교한 뒤
복제본을 삭제한다. 개발 RDS는 이 로컬 검증에 사용하지 않았다.

## 전체 실행에서 발견한 저장 경계

첫 실행은 2026년 9월의 8번째 시군구에서 중단됐다. 기존 정상 거래에는
동 정보와 등기일이 없었고, 새 응답에는 동일한 식별 키의 정상 거래
(동 정보·등기일 포함)와 해제 거래가 함께 있었다. 기존 충돌 사전 검사는
새 정상 원본의 동 정보를 기준으로 두 원본을 별도 거래로 허용했지만,
기존 정상 행은 동 정보를 채우지 않는다. 뒤따르는 해제 원본은 기존
정상 행과 안전하게 분리할 수 없어 저장 단계에서 예외가 발생했다.

기존 거래와 새 원본 모두를 고려하도록 사전 검사를 보완했다. 기존 정상
행에 동 정보가 없으면 정상·해제 원본을 `SOURCE_STATUS_CONFLICT`로
분리하고 기존 행은 변경하지 않는다. 분리 기준을 완화하거나 자동으로
동 정보를 추정하지 않았다. 이 경우의 PostGIS 통합 회귀 테스트를 추가했다.

## 로컬 전체 실행 결과

보완 후 186개 조합을 모두 처리했다. `SUCCESS` 72개, 원본 충돌을 분리한
`PARTIAL` 114개, `FAILED` 0개였고 전체 상태는
`COMPLETE_WITH_CONFLICTS`였다. 원본 충돌 712건 중 새로 관찰된 원본은
346건이다. 복제 DB의 거래 433,635→442,199건, 연결 거래
397,808→405,579건, 충돌 기록 33,684→34,030건이었다. 대표 가격이
있는 단지는 5,609곳으로 유지됐고 가격 합계는
569,117,448→571,815,918만원이었다. 신규 연결은 7,771건이다.
원본 로컬 DB의 비교 대상 집계는 유지됐고 복제 DB는 삭제됐다.
첫 전체 실행은 약 4분 36초가 걸렸다.

같은 복제 DB에서 186개 조합을 다시 실행했을 때도 `SUCCESS` 72개,
`PARTIAL` 114개, `FAILED` 0개였다. 신규 거래와 신규 충돌은 모두 0건,
신규 연결도 0건이었다. 거래·연결·충돌·가격 단지 수·가격 합계는 1회차
직후와 같았다. 2회차에는 약 4분 1초가 걸렸다. 이후 복제 DB를 삭제했고
원본 로컬 DB 집계가 처음과 같은 것을 확인했다.

새 충돌 기록 346건은 `SOURCE_STATUS_CONFLICT` 344건과
`SOURCE_CANCELLATION_DATE_MISMATCH` 2건으로 분류됐다. 전체 원본 충돌
712건과 새 충돌 기록 346건은 서로 다른 지표다. 전자는 이번 API 응답에서
보류한 원본 수이고 후자는 DB에 새로 기록된 검토 대상 수다.
계약월별 신규 거래/신규 충돌은 9월 110/80건, 10월 4,111/200건,
11월 4,343/66건이었다. `PARTIAL` 조합은 각각 50/43/21개였다.

`PARTIAL`은 해당 조합의 모든 원본이 무효라는 뜻이 아니라, 식별 근거가
부족한 일부 원본을 검토 대상으로 보류했다는 뜻이다. 조합별 수치와
사유는 Git에서 제외되는 `data/trade/import-runs/weekly-full-*.tsv`에 있다.
실행 로그도 같은 제외 경로에 저장하고 권한을 `0600`으로 제한한다.

## 개발 RDS 전체 수동 실행

2026-11-21 개발 EC2에서 메모리와 디스크를 확인했다. 인스턴스 메모리는
910MiB, 실행 전 사용 가능 메모리는 313MiB, 디스크 여유는 17GiB였다.
검증용 JAR와 스크립트의 전송 후 SHA-256 해시가 로컬과 같은 것을 확인했다.
개발 API 실행 중에 `pg_dump -Fc` 백업을 만들었고 백업 파일은 약 19MiB였다.
그 후 개발 API를 중지하고 별도 JVM에서 전체 갱신을 수행했다.

수동 실행 로그의 상태는 `COMPLETE_WITH_CONFLICTS`였다. 결과 TSV에는
186개 고유 시군구·계약월 조합이 있었고 `SUCCESS` 72개,
`PARTIAL` 114개, `FAILED` 0개였다. 원본 충돌 712건 중 새 충돌 기록은
346건, 신규 연결은 7,752건이다. 개발 RDS의 거래·연결·충돌·가격 단지
수·가격 합계는 각각 다음과 같이 변했다.

| 항목 | 실행 전 | 실행 후 |
| --- | ---: | ---: |
| 거래 | 433,655 | 442,199 |
| 연결 거래 | 397,827 | 405,579 |
| 충돌 기록 | 33,684 | 34,030 |
| 가격 단지 | 5,609 | 5,609 |
| 가격 합계(만원) | 569,130,248 | 571,815,918 |

검증 스크립트의 마지막 결과 행 수 계산에 `awk` 문법 오류가 있어 스크립트
종료 코드는 1이었다. 전체 갱신 로그의 완료 상태, 결과 TSV의 187줄
(헤더 포함)과 186개 고유 조합·상태 수, 백업 파일, 실행 후 DB 집계는
별도로 확인했다. 오류 표현식을 수정했고 로컬 TSV에서 행 수 계산을
검증했다. 개발 API 서비스는 재시작됐고 공개 health는 `UP`이었다.
이 종료 코드를 전체 갱신 실패로 해석하지 않는다.

## 남은 검증

- `COMPLETE_WITH_CONFLICTS`는 이 작업의 완료 상태다. 원본 충돌 712건은
  식별 근거가 부족한 행을 보류했다는 뜻이며, 이것만으로 예약 실행을
  막는 실패가 아니다. 로컬 동일 범위 재실행에서 신규 충돌은 0건이었다.
- 개발 서버의 수동 검증은 API를 중지하고 별도 JVM에서 실행했다. 현재
  개발 EC2는 메모리 910MiB·스왑 0이고, 평상시 API 서비스는 약
  400~450MiB를 사용한다. Spring `@Scheduled`는 실행 중인 API JVM에서
  갱신하므로 수동 검증으로는 API 동시 실행 시의 메모리와 응답 영향을
  확인할 수 없다.
- `dev` 설정의 외부 실거래 수집과 주간 예약은 모두 기본값이 `false`이고,
  서버 비밀 환경 파일에도 활성화 값이 없다. 수동 검증은 별도 프로세스의
  CLI 인자로만 수집을 활성화했으므로 예약 설정은 바뀌지 않았다.
- 다음 단계에서는 API 동시 실행을 검증하거나, 매주 짧은 API 중지를
  허용하는 별도 예약 배치와 자동 재시작 절차를 정해야 한다. 새 충돌
  사례의 개별 검토는 별도 품질 점검으로 이어갈 수 있다.

## 주간 예약 방식 결정

사용자는 개발 API가 주 1회 약 3분 중단될 수 있는 별도 배치 방식을
선택했다. 기존 EC2의 systemd 타이머를 한국 시간 월요일 03:00에 맞춘다.
타이머가 실행하는 서비스는 위에서 검증한 수동 스크립트를 호출한다.
스크립트는 RDS 백업 후 API를 중지하고, 별도 JVM에서 최대 5분 동안
전체 조합을 처리한 뒤 API 재시작과 health를 확인한다. 셸 복구 트랩 외에
systemd `ExecStopPost`도 API 시작을 재시도한다. 정상 실행은 약
3분이었지만 외부 API 지연이 있으면 중지 시간이 더 길 수 있다.

타이머가 없는 동안 개발 API에서 Spring `@Scheduled`를 켜면 1GiB
EC2에서 웹 요청과 배치를 함께 처리해야 한다. 수동 실행은 API를 중지한
상태에서만 검증됐으므로 이 방식을 사용하지 않는다. `Persistent=false`로
놓친 예약을 부팅 직후 실행하지 않고, 기존 배포 스크립트와 파일 잠금을
공유해 배포·롤백과 겹치면 갱신을 시작하지 않게 한다. 결과 TSV와 백업은
실행별로 보관하며 자동 삭제하지 않는다.

현재 브랜치의 저장 경계 수정이 `main`에 병합되고 개발 API JAR에
배포된 것을 확인한 후 타이머를 활성화한다. 설치만 한 상태에서는
자동 실행되지 않는다.

2026-11-21 EC2에 서비스·타이머 파일과 실행 스크립트를 설치했다.
`systemd-analyze verify`가 해당 단위 파일을 수용했고, 달력 표현식의
다음 실행 시각이 한국 시간 월요일 03:00으로 해석되는 것을 확인했다.
타이머 상태는 `disabled`, 개발 API의 공개 health는 `UP`이었다.
