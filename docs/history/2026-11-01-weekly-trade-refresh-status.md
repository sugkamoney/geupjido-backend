# 주간 실거래 갱신의 완료 판정 범위

## 발견한 문제

주간 작업은 이번 시군구·계약월을 API에서 수집한 뒤, DB의 과거 미연결
거래까지 다시 단지에 연결한다. 처음 구현에서는 연결 단계의 전체
`UNKNOWN_LEGAL_DONG`·권역 불일치 건수가 한 건이라도 있으면 이번
수집을 `NEEDS_REVIEW`로 판정했다.

로컬 DB에는 시군구 코드와 법정동명이 다른 과거 거래 8건이 남아 있다.
성동구 코드의 신당동 3건, 성북구 코드의 청량리동 1건, 강북구 코드의
도봉동 2건, 관악구 코드의 사당동 2건이다. 이 중 사당동 해제 거래
2건과 동일 조건의 동작구 정상 거래가 있어, 법정동명만 보고 코드를
바꾸면 거래 상태를 잘못 합칠 수 있다.

## 결정

단지 연결은 계속 전체 미연결 거래에 실행한다. 결과에는 전체 이상
건수와 이번 수집 조합에 해당하는 이상 건수를 함께 기록한다. 주간
작업의 `COMPLETE`는 모든 시군구·월 수집이 `SUCCESS`이고 이번 조합의
법정동 미확인·권역 불일치가 0건일 때만 사용한다. `PARTIAL` 조합만
남으면 `COMPLETE_WITH_CONFLICTS`로 완료하고 충돌 원본은 보류한다.
수집 `FAILED`가 있으면 전체 `FAILED`, 이번 조합의 연결·권역 이상이
있으면 `NEEDS_REVIEW`로 남긴다. 수집 실패를 우선 판정한다.

과거 8건은 전체 진단 건수에서 계속 드러난다. 이 규칙은 원본의
시군구 코드를 추정해서 수정하지 않으며, 과거 원본 검토가 완료됐다는
뜻도 아니다.

2026-11-01 로컬 PostgreSQL에서 용산구 2026-09 조합을 재실행한 결과,
수집 `SUCCESS`, 신규·갱신·충돌 0건, 이번 조합 미확인·권역 불일치
0건, 전체 미확인 8건, 최종 `COMPLETE`를 확인했다.

같은 날 중구 2026-09 조합을 상태 분리 후 재실행했다. 수집 `PARTIAL`
충돌 4건, 신규·갱신 0건, 이번 조합 연결·권역 이상 0건으로 최종
`COMPLETE_WITH_CONFLICTS`와 프로세스 종료 코드 0을 확인했다. 실행
전후 거래 36건·열린 충돌 4건으로 중복 저장은 없었다.

조합별 결과 파일에는 전체 충돌 원본 수와 이번에 처음 확인한 원본 수를
각각 기록한다. 새로운지 여부는 시군구·계약월과 거래 원본 필드 전체가
V17의 `apartment_trade_conflict_seen`에 이미 있는지 저장 직전에
비교한다. 기존 충돌은 마이그레이션에서 소급 등록하고,
API 응답 순서가 달라져도 이 이력은 유지한다. 이전 형식의
결과 파일은 과거 행을 보존하고 신규충돌 열을 빈칸으로 추가한다.
중구 2026-09를 다시 실행했을 때 충돌 4건, 신규충돌 0건이었다.
V17 시점에는 충돌 테이블이 API 응답 순서 번호로 최신 원본을 갱신했고,
새 충돌 판정 이력만 원본 내용에 별도로 묶어 보존했다. 같은 내용의
응답 순서만 바뀐 통합 테스트에서 신규충돌 0건을 확인했다.

상태와 신규충돌 집계를 적용한 뒤 전체 186조합을 재실행했다. 수집
`SUCCESS` 104·`PARTIAL` 82, 원본 충돌 431건, 신규충돌 0건,
신규·갱신 거래 0건이었다. 최종 `COMPLETE_WITH_CONFLICTS`로 종료 코드
0을 반환했고, DB 거래 433,635건과 가격 있는 단지 5,609곳은
실행 전후 같았다.

V17을 로컬 PostgreSQL에 적용한 뒤 중구 2026-09 조합을 재실행해
충돌 4건 중 신규충돌 0건, 최종 `COMPLETE_WITH_CONFLICTS`와 종료 코드
0을 다시 확인했다.

최종 검토에서 과거 충돌을 해소할 때 API 응답 순번이 바뀌면 검토 행이
열린 채 남는 문제를 확인했다. 동일 계약 조건의 정상·해제 원본을
등기일 근거로 분리 저장한 경우에는 순번 대신 시군구·법정동·단지명·
계약일·금액·면적·층의 거래 조건으로 해당 검토 행을 닫는다.
응답 순서가 바뀐 PostgreSQL 통합 테스트로 확인했다.
운영 프로필에는 실거래 API와 주간 예약 설정을 추가하되 예약 기본값은
꺼짐으로 유지했다. 실제 예약 실행은 서버 배포 후 검증한다.

2026-11-02 검토에서 응답 순서가 바뀌면 같은 원본 내용의 `OPEN` 검토 행이
중복 생성되는 문제를 확인했다. V18은 `apartment_trade_conflict_seen.id`를
검토 행에 연결하고, 기존 중복은 삭제 대신 `SUPERSEDED`로 보존한다.
로컬 PostgreSQL 적용 전 검토 행 33,684행은 모두 원본 내용과 대응했다.
적용 후 전체 `OPEN`은 33,682→32,930행, `SUPERSEDED`는 752행이며,
같은 원본 내용에 대해 여러 `OPEN` 행이 남은 경우는 0건이다.
최근 계약월 2026-09~11의 `OPEN`은 609→451행이다. 이 중 431행은
마지막 전체 재수집에서 확인한 충돌 원본이고, 나머지 20행은 그 실행에서
다시 관찰되지 않은 과거 검토 기록이다. 관찰되지 않은 이유만으로 원본
거래가 사라졌거나 해결됐다고 판단하지 않는다.

V18 적용 후 화성시(41360) 2026-09 조합을 실제 API로 다시 수집했다.
원본 충돌 18행, 처음 확인한 충돌 0행, 신규·갱신 거래 0행으로
`COMPLETE_WITH_CONFLICTS`였다. 이 조합의 `OPEN`은 20→18행이 됐고
2행은 현재 분리 기준으로 `RESOLVED` 처리됐다. `SUPERSEDED` 17행은
그대로 보존됐으며 전체 거래 433,635행과 가격 있는 단지 5,609곳은
변하지 않았다. 중복 `OPEN`은 재실행 후에도 0건이다.

기본 `./gradlew clean build`와 거래 저장·조회 관련 PostGIS 통합 테스트
5개 클래스는 통과했다. 수동 적재 Runner 테스트에는 비활성화된 API 설정을
테스트용 가짜 주소·키로 활성화해 필요한 필터 Bean이 만들어지게 했다.
`RUN_POSTGIS_IT=true` 전체 실행은 별도 지역 경계
GeoJSON의 누락 코드로 `LocationDataImportServiceIT`가 실패했고,
`ApartmentTradeMatchProposalIT`는 전체 거래를 JPA로 읽다가 메모리
부족이 발생해 완료하지 못했다. 두 실패는 V18 중복 방지 테스트와
구분해 기록한다.
