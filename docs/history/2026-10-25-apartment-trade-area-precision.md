# 아파트 실거래가 전용면적 저장 정밀도

## 배경

`V5__create_apartment_trade_table.sql`의 `exclusive_area`는 `NUMERIC(8, 2)`였다. API 응답은 문자열에서 `BigDecimal`로 변환되므로 소수 셋째 자리 이후의 값도 내부 모델에 들어올 수 있다. DB가 이를 두 자리로 반올림하면 저장 값과 재수집 값이 달라지고, 전용면적을 포함한 원본 거래 고유 키로 기존 행을 찾지 못할 수 있다.

## 결정

- 적용된 V5는 수정하지 않고 V6 마이그레이션으로 `exclusive_area`를 `NUMERIC(12, 6)`으로 확장한다. 정수부 여섯 자리의 기존 범위는 유지한다.
- JPA 컬럼 매핑도 precision 12, scale 6으로 맞춘다.
- API 변환과 엔티티 생성에서 유효한 소수 자릿수가 여섯 자리를 초과하면 명시적으로 실패시킨다. 끝의 0은 값의 정밀도를 늘리지 않으므로 허용한다.
- 기존 두 자리 값은 같은 숫자로 보존한다. 전용면적이 고유 키의 일부인 현재 설계는 유지한다.

## 검토한 대안과 영향

- 두 자리 유지: 스키마 변경은 없지만 더 긴 입력을 조용히 반올림해 원본 보존과 재수집 판정이 어긋날 수 있다.
- 무제한 `NUMERIC`: 임의 자릿수를 보존할 수 있지만 저장 계약과 JPA 매핑의 상한이 명확하지 않다.
- 여섯 자리 고정: 저장 계약이 명확하고 범위를 넘는 입력을 오류로 드러낸다. 향후 실제 원본에서 더 긴 유효 자릿수가 확인되면 새 마이그레이션과 검증 규칙을 함께 조정해야 한다.

로컬 PostgreSQL 통합 테스트에서 소수 여섯째 자리만 다른 두 거래가 별도 행으로 저장되고, 같은 입력을 다시 처리하면 두 행 모두 중복으로 건너뛰는 것을 확인했다.
