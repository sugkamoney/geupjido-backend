# 급지도 작업 재개 점검

- 상태: 조사 기록·일부 기준 확정·포일동 매핑 반영
- 확인일: 2026-10-25
- 관련 이슈: [#73](https://github.com/sugkamoney/geupjido-backend/issues/73)
- 범위: 백엔드 현황, 기존 기획, 디자인 1차 전달, 프런트엔드 문서 운영, AI 협업 방식

이 문서는 작업 재개 시점의 근거와 미결정 사항을 기록한다. 5.x 급지, 포일/내손 통합 162권역, AI 코드 작성 범위는 사용자와 합의했다. 권역 경계와 초기값 등 나머지 제품 정책은 확정하지 않는다. 다음 구현 이슈를 열 때 최신 기획·디자인 및 실제 코드를 다시 확인한다.

## 확인된 현재 위치

- 백엔드의 최근 완료 작업은 월별 아파트 매매 실거래가 API 수집과 DTO 변환이다. `ApartmentTradeCollectionService`의 결과를 DB에 저장하는 서비스는 아직 없다. 사용자용 Controller와 운영 배포도 완성 전이다. [백엔드 인수인계](2026-10-23-orca-handoff.md)
- 백엔드 `AGENTS.md`는 사용자의 핵심 비즈니스 로직 직접 작성과 최종 설계 판단, AI의 단계별 안내·검토 및 합의된 범위의 설정·반복 코드·테스트·문서 작성을 규정한다.
- [기존 기획 허브](https://app.notion.com/p/3c79bfb122db8091bbc5d6e329dab3cc)의 비보관 기능 7건과 기획 논의 16건은 원문을 확인했다. Implementation 81건은 목록·상태를 확인했고 본문은 충돌 사례 등 4건만 읽었다. 8월 구현 보드의 `작업 준비` 상태를 최신 정책이나 실제 구현의 증거로 사용하지 않는다.
- [10월 8일 디자인 1차 핸드오프](https://app.notion.com/p/3f39bfb122db8026a564cb622f19c912)는 데스크톱 지도·권역 상세·검색·월드컵 전달을 완료로 표시한다. 랭킹·리포트 화면과 모바일 완성본은 전달 범위에 포함되지 않는다. 이는 디자인 전달 상태이며 백엔드·프런트엔드 구현 완료를 뜻하지 않는다.
- [프런트엔드 저장소](https://github.com/sugkamoney/geupjido-frontend)의 `develop`은 `docs/README.md`, `docs/INDEX.md`, 제품 명세, 아키텍처, 번호형 학습 Q&A, ADR, PR 템플릿을 운영한다. 백엔드에는 `AGENTS.md`에서 지정한 `docs/architecture/`, `docs/learning/backend/q-and-a/`, `docs/history/`가 아직 없다.

## 다음 기능 전에 반드시 확인할 내용

1. **포일동 포함:** 2026-10-23 결정으로 **포일/내손 한 권역, 총 162권역**을 기준으로 한다. 이 브랜치에서 `uiwang-naeson` 권역에 내손동 `4143010700`과 포일동 `4143010900`을 함께 배정했다. 로컬 VWorld 경계로 PostGIS 적재와 두 법정동의 공간 포함을 확인했다. 실제 단지의 권역 연결은 아직 구현되지 않았으므로 검증하지 못했다. 기존 [경계·이름 확정 카드](https://app.notion.com/p/3c89bfb122db81da9f95eedbd2ec965a)의 나머지 권역 검토는 계속 필요하다.
2. **급지 값 범위:** [9월 기획](https://app.notion.com/p/3c79bfb122db815d8cd9d96f384b69bc)의 1.0~5.0 표기는 사용자가 제시한 `배치표(단가 포함)-update.pdf`와 2026-10-23 결정에 따라 **1.0~5.9**로 정정한다. PDF 1쪽에는 5.1~5.9 행이 있으며 기흥 5.1·병점 5.4가 매핑과 일치한다. Flyway V3도 5.9까지 허용한다. 지도 색·라벨·API의 5.x 표현 규칙은 디자인과 확인해야 한다.
3. **초기 급지와 전환:** [9월 11일 전환 카드](https://app.notion.com/p/3d89bfb122db80abbd82f7fa395502d0)는 논의 중이고 최종 결정이 비어 있다. 초기값의 데이터 근거, 투표 영향 증가 방식, 공식 민심급지 전환 표본수, 오픈 방식은 미정이다.
4. **투표·집계 정책:** 익명 식별과 중복·넘김 처리, 대진 생성, 비율 공개 기준, 지도 반영 주기를 API·저장 모델 구현 전에 명시해야 한다. 디자인 첨부의 40/80 등장 횟수, 6권역+4단지 대진, 비율 표시 10명 등은 시안의 가정이다. [디자인 핸드오프](https://app.notion.com/p/3f39bfb122db8026a564cb622f19c912)
5. **지도 좌표:** 디자이너 문서에 경계·단지 위치가 네이버 지도 기준 동쪽 약 180m·남쪽 약 310m 어긋난다는 관찰이 있다. 원본 좌표계와 변환 과정을 샘플 좌표로 검증해야 한다. 현 첨부 파일과 로컬 사본의 바이트 단위 동일성은 확인되지 않았다.
6. **화면 우선순위:** [9월 모바일 중심 결정](https://app.notion.com/p/3c79bfb122db817ab82cc80714d3971e)과 10월 데스크톱 **1차 전달 범위**를 구분하고, 모바일 설계·구현 일정은 프런트엔드·디자인 담당자와 확인한다.

## AI 활용 논의의 출발점

[사용자가 제공한 영상](https://www.youtube.com/watch?v=_ueKbN_LAyI)의 스크립트는 사용자 문제 탐색, 서비스 정책 결정, AI가 작업할 수 있는 환경 구성, 결과 검증과 실제 운영 경험을 강조한다. `2027년 개발자 포지션이 사라진다`는 발언은 발표자의 전망이며 이 프로젝트의 사실이나 정책으로 기록하지 않는다.

급지도에서는 이슈마다 **문제와 사용자 가치 → 사람의 결정 → AI에 맡긴 범위 → 검증 근거 → 배포·사용자 피드백**을 남기는 방식을 제안한다. 사용자는 핵심 비즈니스 로직을 직접 작성하고 최종 정책·설계를 판단한다. AI는 합의된 범위의 설정·반복 코드·테스트·문서를 작성하고 근거와 검증 결과를 설명한다. 실제 사용자·운영 지표가 아직 없다면 성과로 표현하지 않는다.

### 이슈 #73에서 실제로 AI를 사용한 방식

| 단계 | 기록 |
| --- | --- |
| 문제와 사용자 가치 | 기존 기획의 163권역 표기와 백엔드 162권역 매핑이 달랐고, 포일동이 매핑에서 빠져 있었다. 작업 재개 시 설계 기준과 실제 데이터를 맞출 필요가 있었다. |
| 사람의 결정 | 사용자가 제공한 배치표 PDF를 급지 기준으로 삼고 5.x를 유지했다. 포일/내손을 한 권역으로 묶고, 포일동 매핑도 현재 브랜치에 포함하기로 결정했다. 핵심 비즈니스 로직과 최종 제품 정책은 사용자가 맡는 혼합형 AI 협업 방식을 선택했다. |
| AI에 맡긴 범위 | 기획·설계·코드 차이 조사, 이슈 #73의 범위 정리, 협업 규칙·인수인계 문서 작성, 기존 권역 매핑과 검토 TSV 수정, 포일동 경계의 로컬 확보, 매핑·PostGIS 테스트 작성과 실행, Notion 기록 갱신을 맡았다. |
| 검증 근거 | 162권역·254개 법정동 코드, 실제 포일동·내손동 경계가 한 권역 도형에 포함되는 PostGIS 통합 테스트 3건 통과, `./gradlew clean build` 성공을 확인했다. |
| 배포·사용자 피드백 | 아직 커밋·PR·배포 전이며 실제 사용자 검증과 운영 지표는 없다. 실제 단지 연결도 구현 전이다. 이 단계는 후속 이슈에서 증거가 생길 때 갱신한다. |

이 기록은 AI가 작성한 범위와 검증 결과를 구분하기 위한 첫 사례다. 후속 이슈에서도 같은 항목을 채우되, 실행하거나 관찰하지 않은 결과는 완료로 적지 않는다.

## 프런트엔드에서 가져올 문서 운영 방식

- `docs/README.md`와 `docs/INDEX.md`로 문서의 위치와 현재 기준을 찾을 수 있게 한다.
- 설계·결정 문서에 `제안 / 확정 / 대체됨` 상태와 최종 변경일을 표시한다.
- 기술·제품 결정에는 대안, 선택 이유, 재검토 조건을 기록하고, 학습 Q&A에는 실제 백엔드 코드 적용 사례를 붙인다.
- 백엔드 인수인계에 적힌 PR 본문 항목을 저장소 PR 템플릿으로 옮기는 것은 후속 문서 작업 후보로 둔다.

이 항목들은 도입 제안이다. 프런트엔드의 화면 명세 구조나 AI 코드 작성 규칙을 백엔드에 그대로 적용하기로 결정한 것은 아니다.

## 다음 작업 순서 제안

1. 이슈 #73의 인수인계·재개 점검·AI 협업 문서와 포일/내손 매핑 변경을 리뷰한다. 이슈 제목은 현재 범위로 변경했고 브랜치명은 유지했다.
2. 로컬 전용 경계 파일이 없는 환경에서는 `python3 -B scripts/location/download_boundaries.py`로 매핑에 맞는 경계를 다시 받는다. 이 파일은 Git 추적 대상이 아니다.
3. 각 후속 이슈에서 핵심 로직과 AI 담당 범위를 먼저 구분하고, 작업 결과를 검토한다. 실제 단지 연결은 해당 기능 구현 시 포일동 사례로 검증한다.
4. 남은 제품·디자인 충돌은 담당자와 결정해 Notion에 반영한다. 다음 별도 기능 이슈인 월별 실거래가 저장 서비스는 중복 처리·실패 시 트랜잭션·단지 연결 범위를 먼저 정한다.
