# 실거래가 원본·단지 연결 검토 파일

> **2026-10-30 현재 규칙:** 아래의 연도 일치 설명은 최초 검토 시점의
> 기준을 기록한 것이다. 현재 자동 연결과 승인 제안 적용은 단지 사용승인연도와
> 거래 건축연도를 비교하지 않는다. 법정동·지번·단지명 또는 검증된 별칭,
> 분양형태·권역·기존 연결 충돌을 확인한다. 건축연도는 원본 거래를 식별하는
> 키에는 계속 포함한다. 도로명주소만 일치하고 이름이 다른 후보는 검토한다.

> **적용 기준:** 현재 `location-mapping.json`의 권역 정의를 유지한다.
> PDF의 지명 차이를 이유로 권역을 변경하지 않는다. 사용자가 확인한
> 12조합만 `APPROVED`다. `리첸시아용산A`와 `한성1`은 `PENDING`이며
> 연결하지 않는다. 원본 거래는 그대로 보관한다.

`yongsan-202609-proposals.tsv`는 2026년 9월 용산구 로컬 거래에서 발견한
**14개 원본 단지명·법정동·지번·건축연도 조합**과 현재 단지 마스터 후보를 담는다.
14개 조합에 해당하는 거래는 18건이다. 이 중 12조합(거래 16건)은
사용자 승인에 따라 `APPROVED`, 2조합(거래 2건)은 `PENDING`이다.
각 조합의 공식 주소·사용승인일 재확인 결과는
[`yongsan-202609-review.md`](yongsan-202609-review.md)에 있다.

각 행의 `판정`은 후보 탐색 결과다. `NAME_EXACT`는 공백을 제외한 이름이 같다는
뜻이고, `NAME_REVIEW`는 이름이 다르다는 뜻이다. 이 표본을 검토할 당시에는
두 상태 모두 수동 확인 후에만 `APPROVED`로 변경했다. 현재 후보는 같은 10자리
법정동 코드, 정확한 지번, 같은 건축·사용승인연도, 단일 후보 및 권역 존재를
만족했다. 다른 단지라고 확인되면 `REJECTED`로 바꾼다.

첫 열 `계약월`은 `yyyyMM` 형식이며 승인 범위의 일부다. 같은 원본명·주소라도
다른 계약월은 별도 행으로 검토·승인해야 한다. 한 파일에 여러 지역과 계약월을
담을 수 있지만, 각 행이 실제로 해당 거래를 가리키는지 확인해야 한다.

수동 적용은 일반 서버 실행에서 꺼져 있다. 승인 후 다음처럼 한 번 실행한다.

```sh
./gradlew bootRun --args='--spring.main.web-application-type=none --app.apartment-trade-match.enabled=true'
```

기본 검토 파일은 2026년 9월 용산구 표본이다. 다른 검토 파일을 적용할 때에는
`APARTMENT_TRADE_MATCH_PROPOSAL_PATH`를 지정한다. 참조 파일과 권역
매핑을 바꾸려면 `APARTMENT_TRADE_MATCH_REFERENCE_PATH`,
`APARTMENT_TRADE_MATCH_MAPPING_PATH`를 지정한다. 이 작업은 승인된 행만
거래에 적용하고, 한 번에 트랜잭션으로 처리한다.
동일한 연결을 다시 실행하면 `이미 연결`로 집계한다. 기존의 다른 연결은
덮어쓰지 않고 실패한다. 다른 승인 행에서도 오류가 발생하면 이번 실행의
연결 전체가 롤백된다.

파일 이름의 `202609`와 각 행의 `계약월`은 **2026년 9월 계약 거래**를 뜻한다.
같은 이름·지번·연도의 다른 달 거래는 이번 실행에서 연결하지 않는다.
이 수동 실행은 첫 검증 표본과 이름이 다른 후보의 개별 검토에 사용한다.
새 월과 지역에 같은 승인 파일을 그대로 적용하지 않는다.
이는 승인 파일을 직접 적용하는 범위다. 아래 엄격 연결 실행은 이미 DB에
검증 연결된 거래와 원본 식별 조합이 완전히 같은 다른 달 거래를 별도로
재검증해 연결한다.

2026-10-29부터는 사용자의 전체 연결 요청에 따라 **엄격 일치** 거래에 한해
별도의 수동 실행 경로가 있다. 서비스 대상 법정동, 정확한 지번의 후보,
공백을 제외한 동일 단지명, 거래 건축연도와 단지 사용승인연도 일치, 거래
법정동 코드 일치와 단지에 실제 배정된 권역 존재를 모두 만족할 때만
`complex_id`와 `zone_id`를 함께 저장한다. #101에서 한 법정동을 공간 경계로
둘 이상의 권역으로 나눈 경우에는 법정동의 기본 권역 대신 해당 단지의
실제 권역을 사용한다. 지번 후보가 여러 개면 거래명과 같은 이름 또는
기존 승인 별칭의 단지가 딱 하나이고 그 단지의 분양형태가 `분양` 또는
`혼합`으로 확인된 경우에만 선택한다. `417`과 `0417-0000`처럼 숫자로
표기된 지번이 같은 경우도 분양형태가 확인된 단지에 한해 같은 지번으로
취급한다. 실제 지번 숫자가 다르면 자동 연결하지 않는다.
이름이 다른 후보, 해결되지 않은 복수 후보, 연도 불일치·누락,
단지의 권역 누락, 서비스 대상 밖 거래는 자동 연결하지 않는다. 기존의 다른 연결도
덮어쓰지 않는다.

```sh
./gradlew bootRun --args='--spring.main.web-application-type=none --app.apartment-trade-match.auto-exact-enabled=true'
```

`APARTMENT_TRADE_MATCH_AUTO_EXACT_ENABLED=true` 환경 변수로도 켤 수 있다.
기본값은 `false`다. 거래를 500건씩 별도 트랜잭션으로 처리하므로 중간에
실패하면 이미 끝난 구간은 남고, 재실행 시 연결된 거래를 건너뛴다. 연결이
끝나면 같은 실행에서 `complex`의 59㎡ 대표 시세와 잠정 순위를 재계산한다.
API 소급 수집과 연결은 실행 순서가 중요하므로 별도의 실행으로 진행한다.
이미 검증된 거래의 시군구·법정동명·지번·거래명·건축연도 조합이 정확히
같고, 과거 연결이 단지·권역 ID를 각각 하나씩만 가리키면 다른 계약월에도
그 연결을 재사용한다. 현재 단지의 법정동 코드·실제 권역·사용승인연도와 임대 전용
여부를 다시 검사한다. 원본 이름이나 지번이 바뀌면 같은 조합이 아니므로
이 규칙만으로 새 표기까지 자동 연결되지는 않는다.

기존 DB 거래 전체의 분류·후보·연결 상태는 읽기 전용 수동 점검으로 확인한다.

```sh
./gradlew bootRun --args='--spring.main.web-application-type=none --app.apartment-trade-match.audit-enabled=true'
```

결과는 기본적으로 `build/reports/apartment-trade-match-audit.tsv`에 저장된다.
`APARTMENT_TRADE_MATCH_AUDIT_PATH`로 경로를 바꿀 수 있다. 거래 한 건마다
서비스 범위, 법정동 코드, 법정동의 기본 권역, 연결 상태, 미연결 거래의 후보 판정과 후보
단지 ID를 기록한다. `build/` 결과는 Git에서 제외된다. `INCONSISTENT_LINK`가
있으면 기존 단지·권역 연결을 검토해야 한다. 법정동 기본 권역과 단지의 실제
권역이 다른 것만으로는 불일치가 아니다. 점검은 거래 DB 값을 수정하지
않으며, 승인 파일 적용과 별도로 실행한다.

거래별 결과가 많을 때는 `python3 -B scripts/trade/summarize_match_audit.py
build/reports/apartment-trade-match-audit.tsv`로 지역별 상태와 이름 검토
조합을 묶을 수 있다. 결과는 `build/reports/trade-status-by-district.tsv`,
`build/reports/trade-unlinked-groups.tsv`,
`build/reports/trade-name-review-groups.tsv`다. 후자는 우선 검토 대상을
고르기 위한 자료이며, 묶인 조합을 승인한 것으로 간주하지 않는다. 실제
연결 승인은 위의 계약월별 검토 파일로 진행한다.
단지 마스터의 `id,name,address_jibun,address_road,approval_date,zone_id`
열을 CSV로 내보낸 경우 `--complex-master 경로.csv`를 추가하면 검토 목록에
후보 단지의 이름·주소·사용승인일도 함께 표시한다.
이 경우 `trade-address-review-groups.tsv`도 생성한다. 같은 법정동·권역에
이름이 같은 단지가 하나 있지만 거래 지번과 단지 주소가 달라 후보에서 빠진
조합의 검토 목록이다. 이 목록만으로 연결을 승인하지 않는다.
정상·중개·59㎡ 거래의 `id` 열을 CSV로 내보낸 경우
`--eligible-trade-ids 경로.csv`를 추가하면 해당 거래 건수 순으로 정렬해
대표 시세에 영향이 있는 검토 조합부터 볼 수 있다. 이 CSV는 로컬 점검
자료이며 Git에 추가하지 않는다.

같은 지번 후보가 없는 거래 5건과 서비스 범위 밖 거래 11건은 이 파일에 승인
대상으로 넣지 않았다. 조사 근거와 처리 기준은
[`docs/history/2026-10-28-trade-complex-matching-scope.md`](../../../docs/history/2026-10-28-trade-complex-matching-scope.md)에 있다.

### 분양형태를 고려한 자동 연결

기본정보 API의 `codeSaleNm`을 `complex.sale_type`에 원문으로 저장한다.
`임대`처럼 임대만 표시된 단지는 매매 실거래의 후보에서 제외한다.
`혼합`은 분양 세대가 있을 수 있으므로 제외하지 않는다. 분양형태가 아직
없는 단지는 임의로 임대라고 추정하지 않으며 기존 검증 규칙을 적용한다.
분양형태 컬럼에 별도 인덱스는 만들지 않았다. 후보 조회는 이미 인덱스가 있는
법정동 코드로 좁혀진다.

이름의 공백만 다른 거래는 종전처럼 일치한다. 그 밖의 이름 차이는 범용
부분 문자열 규칙으로 확정하지 않는다. 실제 주소·단지 ID가 확인된
`신당동 844 · 남산타운 → A10045302`,
`황학동 2545 · 롯데캐슬 → A10044002`만 승인 별칭이다.
두 경우에도 단일 분양 후보, 건축·사용승인연도 일치, 권역 일치를 다시
확인하고 연결한다. 새로운 이름 차이는 `NAME_REVIEW`로 남겨 검토한다.

자동 연결을 재실행하면 분양형태가 확인된 임대 전용 단지의 **과거 연결도
해제**한 뒤 미연결 거래를 검사한다. 거래 원본 행은 삭제하지 않는다.
대표 가격 계산에서도 임대 전용 단지는 제외한다. 분양형태 보충이 아직
완료되지 않은 DB에서는 미확인 단지의 과거 연결을 자동 해제하지 않는다.
